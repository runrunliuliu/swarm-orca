# 自建常驻服务的加固清单（存档，不立项）

状态：**存档参考，不立项、不排期**。本文不是实现计划，也不构成部署或服务变更授权。

用途：如果将来确实需要一个常驻服务（例如跨 worktree 的事实广播、共享证据查询），先按此清单自查，
避免重踩已实测的坑。清单来自对 SwarmChat 0.1.0 服务端实现的只读审阅与本地复跑（调研记录见父工作区
`docs/swarmchat-20261109.md`，不在本仓库）；**不引入其代码或依赖**。

## 为什么现在不建

- 单进程 Python `ThreadingHTTPServer`，1,000 个并发 wait 时约 2,000 req/s 见顶；约 500 agent 请求/秒即吃满一个核。
- 一个 `wait` 占一个 OS 线程（32 个并发 wait = 34 线程），扇出成本随等待者线性增长。
- 每用户 32 个在途请求，逼得"一个 Agent 一个 token"；`send` 无幂等（`retry_safe=False`）；日志无 compaction。
- 结论：我们当前规模用文件 + 单写者足够；引入服务的收益不抵运维与信任边界成本。

## 清单

| # | 项 | 不做的后果 |
| --- | --- | --- |
| 1 | **身份先于请求体**：token 不通过就一个字节 body 也不读 | 未认证请求可用带宽/内存拖垮进程 |
| 2 | **分层 deadline**：请求行+头一个超时；body 按"超时 + 大小/最小速率"；TLS 握手同一时限 | Slowloris 型慢发可长期占住槽位 |
| 3 | **连接三态**：空闲等待 / 请求在途 / 拒绝。挤掉**最久空闲**那条，在途永不打断，只在全部在途时回 503 | 全局限流会杀掉正在干活的请求，或让空闲长连接占满资源 |
| 4 | **fd 预算**：连接上限取 `min(配置, 可用 fd // 2)`，另一半留给日志与上传 | 跑起来先 EMFILE，且日志也写不进去 |
| 5 | **监听 backlog 与 Nagle**：backlog 在 listen 前设大（实测默认 5 会丢约 20% 同时连接的客户端）；对答复关 Nagle（否则每请求多 ~40 ms） | 高并发启动期丢连接、小包延迟翻倍 |
| 6 | **按 recipient 分通知**：每个接收者一个条件变量，只唤醒相关等待者 | 全局广播造成惊群，放大延迟与 CPU |
| 7 | **不要 thread-per-wait**：阻塞型长等待换成事件驱动或文件通知 | 等待者数量直接变成线程与内存成本 |
| 8 | **写前算磁盘**：剩余空间低于阈值拒绝写（507）；上传**先占配额再读字节**；删除操作永不因空间被拒 | 写满磁盘后连清理都写不进去 |
| 9 | **大结果集硬上限 + cursor**：单次返回有上限，余量给游标由调用方续取 | 一次 dump 打爆调用方上下文或内存 |
| 10 | **按调用方能力降级**：如压缩只给声明支持的客户端，CLI/模型侧保持原样 | 全局变换逼所有客户端实现解码 |
| 11 | **只读模式复用同一实现**：观察者入口以 `read_only` 启动，不写状态、不落位置 | 只读靠纪律维持，误用即可写 |
| 12 | **幂等键**：发送侧承担"至多一次"（本项目缺此项） | 断线重试产生重复副作用，且无法判定 |
| 13 | **归档与压缩**：日志只增不减会膨胀（百万消息约 179 MB），需按保留期归档 | 长时间运行后启动与扫描变慢 |
| 14 | **并发上限按调用方而不是全局**：否则单个 Agent 可占满所有槽位 | 一个异常客户端拖垮全体 |

## 使用方式

- 立项前先回答：清单 12（幂等）与 11（只读模式）是否已具备；缺任一项就不要对外暴露写接口。
- 清单 5、8 属于"上线前必须实测"的项，不接受纸面通过。
- 与 [投递台账](delivery-ledger.md) 的分工：台账负责"谁在何时收到/确认了什么"，服务只负责传输；
  台账不依赖服务存在，服务也不能成为台账的唯一真相源。
