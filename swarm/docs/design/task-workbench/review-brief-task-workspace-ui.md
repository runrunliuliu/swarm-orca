# 评审 brief：任务工作台（task workspace）UI 设计

这是**只读、多轮**的独立评审。你不修改仓库、不提交、不部署、不启动其他 Agent。

你先独立出稿（看不到另一位评审者的稿）；之后我会只就仍有分歧的点追问第 2..N 轮。追问时只回答被点名的项，
不要重述全文，也不要为了配合我而改结论——如果你的判断变了，写清楚是哪条新证据让它变的。

## 焦点

**任务工作台 = 点开一个任务后看到的那一屏**（设计文档里的"图 B"）。它是这次讨论的唯一主对象；
列表页（图 A）只在它与工作台的边界上讨论。T2 的底部 dock 与草稿行（§7.9）是本轮**上下文**，不是评审对象。

我的判断（请证伪或确认）：工作台是基础——因为"任务 → 工作区(0..N) → Agent → 用量 → 交付证据"这套 IA
一旦定下来，列表行语义、侧栏草稿行、计数分组、T2 的演化方向都跟着它走；反过来先抠 dock 细节，
很可能为一张还没定的底图做局部优化。

## 必须回答的问题

每条给**结论 + 理由 + 证据（文件路径或行）**；没有证据就写"未验证"，不要用"通常/一般来说"代替。

1. **IA 是否成立**：任务详情以"任务 → 工作区(0..N) → Agent(活/保留/历史) → 用量 → 交付证据"为主轴，
   是不是正确的抽象？有没有更基本的一层被漏掉（例如"任务的目标/验收"、或"任务与 issue 的映射"）？
2. **图 B 的三区布局**（左 Agents / 右 Workspaces+Spend / 底 Delivery）在下列条件下成立吗：
   0 个工作区、1 个工作区、3+ 个工作区；10+ agent；窄窗（<1100px）；窗口高 480px。
   每一条给"会坏在哪"和"应该先牺牲哪一区"。
3. **UI 先行是否可行**：`taskRecords` 尚未落库（M2a 未判决）。工作台 UI 能否先建在"渲染层投影 + 现有
   worktree 数据"上，而不用等存储？如果能，哪些字段/交互必须先有持久化才能做，哪些不需要？
   如果不能，请指出具体是哪一屏/哪个交互无法投影。
4. **图 A 与图 B 的关系**：列表分组（Needs you / Working / Delivered + `◇` 徽标、唯一归属）是否可解释？
   一个任务 `0 工作区`、`2 工作区`、`已归档`、`无 tracker` 时，它在列表里的归属是否仍然唯一且稳定？
5. **与现有 tracker 详情的关系**：issue/PR 详情页（今天的 `GitHubItemDialog` / `PullRequestPage`）保留、
   并存、还是被工作台替代？M1 的 `Orca` tab（§7.4）与 M2b 工作台是否重复？如果重复，砍哪一个？
6. **侧栏与工作台的关系**：一个任务 N 个工作区时，侧栏怎么表现（每个工作区一行？任务一行 + 子行？只显示
   primary？），才不至于让"任务行 / 草稿行 / 工作区行"三种语义互相打架？
7. **用量与证据的落位**：逐 Agent 只显示 token、金额只到工作区/任务级（R2）——在任务级合计里够用吗？
   三态（可用/未启用/不可用）放在哪一区、占多少视觉权重？
8. **主操作**：`Open workspace` / `Create workspace` / `Archive` / `Set primary` / `Resume session` 怎么排，
   才不会在 0 工作区与 N 工作区两种状态下都显得错位？
9. **入口分工是否可解释**：Tasks 工作台、Agent Dashboard、Activity feed、AI Vault 四者的边界，用户会不会
   选错？如果会，请给一个具体误选场景和最小修法（文案/位置/命名）。
10. **如果只能做一版**：给出你认为最小可交付的工作台形态（要什么、砍什么、代价），并与 §7.4 的"只加
    Orca tab"方案比较——哪个更值得先做、为什么。

额外的判断题（请明确回答）：**2026-11-09 的 panel 结论是"先 M1 只读面板，M2 冻结到 M2a"。
在 `taskRecords` 还没落库的前提下，现在冻结工作台的 UI 设计，是加速还是返工风险？**

## 输出（必须照做）

写到 **`/tmp/ws-ui-review-r<N>-<你的 agent 名>.md`**（N 为轮次，从 1 开始）。先写 `.tmp` 再 `mv`，
一次原子写入；写完只打印 3–5 行摘要。

固定顺序：

1. `decision`：一句话（接受 / 接受但需改 / 不接受换方案），并注明针对的是"哪一版图"
2. `verdict-on-focus`：工作台是不是基础？是/否 + 一句理由
3. `options`：你建议比较的替代 IA（每条一句 + 证据）
4. `open`：无法从仓库确认的点
5. `answers`：逐条回答 10 个问题（每条结论一行 + 理由一行）
6. `must-fix`：进实现前必须改的（≤5，按严重度）
7. `nice-to-have`：可后置的（≤5）
8. `end-state`：`decided` / `insufficient-evidence` / `escalate-value-choice`
